\chapter{Project Management}\label{ch:project-management}

\section{Agile Management Process}\label{sec:agile-management-process}

The project followed an interactive development approach using Gitlab for issue tracking and planning.
We defined our project management in a Scrum-like manner, but we individualized the process according to the projects scope and our needs.
Work items where organized into epics, milestones and issues.
Each iteration lasts two weeks.
We decided to hold the following Scrum ceremonies after each sprint:

\begin{itemize}
	\item Sprint planning
	\item Sprint review
	\item Sprint retro
\end{itemize}

The workflow used for ticket tracking consisted of the following stages:

\paragraph{Issue Lifecycle:}
\begin{itemize}
	\item Backlog
	\item Todo
	\item Q\&A
	\item Done
\end{itemize}

\section{Definition of Ready (DoR)}\label{sec:definition-of-ready}

A ticket is considered ready for implementation when the following criteria are fulfilled.

\paragraph{Clarity:}
\begin{itemize}
	\item Clear and precise title
	\item Objective or problem described in two to three sentences
	\item Scope clearly defined
\end{itemize}

\paragraph{Scope:}
\begin{itemize}
	\item Affected module specified (drill, scenario, core, container, frontend)
	\item External dependencies identified
\end{itemize}

\paragraph{Validation:}
\begin{itemize}
	\item Testable acceptance criteria defined
	\item Expected behavior clearly specified
\end{itemize}

\section{Definition of Done (DoD)}\label{sec:definition-of-done}

A ticket is considered done when all the following criteria are fulfilled.

\paragraph{Implementation:}
\begin{itemize}
	\item All acceptance criteria fulfilled
	\item Container execution verified
	\item Pre-commit hooks pass
	\item Logging and error handling consistent
\end{itemize}

\paragraph{Testing:}
\begin{itemize}
	\item Feature or bug fix tested
	\item Acceptance criteria verifiable (automated or manual)
	\item Relevant edge cases considered
	\item Execution reproducible
\end{itemize}

\paragraph{Documentation:}
\begin{itemize}
	\item README updated if required
	\item Architecture changes documented
	\item Thesis relevance briefly noted
	\item Limitations documented
	\item Required documentation stored for thesis or appendix
\end{itemize}

\section{Project Structure}\label{sec:project-structure}

\paragraph{Milestones} represent crucial steps toward the overall project goal.
Per our definition a milestone has at least one epic.

\paragraph{Epics} consist of multiple stories and contribute to fulfilling milestones.

\paragraph{Stories} Each story is assigned a weight, sprint, milestone and epic and are usually represented by an \enquote{Issue} in gitlab.
While Gitlab differences between \enquote{Task} and \enquote{Issue}, the terms are often used interchangeably with \enquote{Stories}.
Stories must meet the~\ref{sec:definition-of-ready} before implementation and~\ref{sec:definition-of-done} before closing.

\section{Planning and Estimation}\label{sec:planning-and-estimation}

The following estimation strategy was used:

\begin{itemize}
	\item 1 hour corresponds roughly to 1 weight point
	\item Iteration length: 2 weeks
	\item Weights per iteration: ~40h per person = ~80 weight per iteration
	\item Sprint planning duration: 1.5 hours per iteration
	\item Sprint review duration: 1 h per iteration
	\item Sprint retro duration: 1 h per iteration
\end{itemize}
