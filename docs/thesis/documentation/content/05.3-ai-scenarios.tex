\section{AI Scenarios}\label{sec:ai-scenarios-implementation}

This section describes the design and implementation of the milestone \gls{AI} Scenarios~\ref{subsubsec:milestone-ai-scenarios},
which is based on the user story map workshop \gls{AI} Purple Team~\ref{sec:nsak-scenario-ai-purple-team}.
In the workshop we defined the features which such a scenario may provide and categorized them in \enquote{Must}, \enquote{Could} and \enquote{Should}.
Because of time constraints, we set the focused only on the user stories categorized as \enquote{Must}.
The main goal is to implement an \gls{AI} reconnaissance scenario, which is described in the~\ref{subsec:scenario-ai-reconnaissance}.
But on the way it made sense to also create an intermediary scenario which can run custom prompts~\ref{subsec:scenario-ai-agent}.
Further, we already explored the \gls{AI} based intrusion detection scenario~\ref{subsec:scenario-ai-intrusion-detection}
which should be seen as proof of concept, because the corresponding milestone and goals are categorized as \enquote{Should}.

\subsection{\gls{AI} Agent}\label{subsec:ai-scenarios-implementation-ai-agent}

An \gls{AI} agent is an autonomous system that combines a large language model (\gls{LLM}) with a set of tools it can invoke to accomplish a goal.
Rather than just generating text, the agent follows a reasoning loop: it plans which tool to call, executes it,
observes the result, and continues until the task is complete~\cite{the-rise-of-agentic-ai}.

The project team chose \href{https://www.langchain.com/}{LangChain} as the agentic framework without comparing it with alternative solutions, for the following reasons:

\begin{itemize}
    \item Free and open-source
    \item Python package with native integration into the project's toolchain
    \item Suggested by various sources and has a good reputation in the community
    \item Extensive documentation and active community support
\end{itemize}

For the integration into the \gls{NSAK} framework we decided to implement an \mintinline{python}{AiAgent} class as the central abstraction,
which wraps a \mintinline{python}{BaseChatModel} together with a set of LangChain tools and delegates the reasoning loop to LangChain's built-in \mintinline{python}{create_agent()}.

\subsubsection{AI Configuration}\label{subsubsec:ai-configuration}

Before any \gls{AI} based scenario can run, the \mintinline{python}{AiConfiguration} entry must be set in the runtime configuration,
containing the model, provider and credentials.
Listing~\ref{lst:ai-configuration} shows the dataclass, which holds two fields: \mintinline{python}{model} and \mintinline{python}{base_url}.
For authentication, the basic auth can be provided in the \mintinline{python}{base_url} field,
otherwise the \mintinline{python}{api_key} must be set.

With the \gls{CLI} command \mintinline{bash}{nsak config set ai} the configuration can be set interactively,
alternatively the values can be set individually like in the following example:

\begin{itemize}
    \item \mintinline{bash}{nsak config set ai\.provider "ollama"}
    \item \mintinline{bash}{nsak config set ai\.model "qwen2.5:7b-instruct"}
    \item \mintinline{bash}{nsak config set ai\.base\_url "http://user:pass@localhost:11434"}
    \item \mintinline{bash}{nsak config set ai\.api\_key "secret"}
\end{itemize}

\subsubsection{Provider Abstraction}\label{subsubsec:ai-provider-abstraction}

The \mintinline{python}{AiAgent.create_model()} method parses the provider prefix and dispatches to the appropriate LangChain chat model class via \mintinline{python}{PROVIDER_MAP},
as shown in listing~\ref{lst:langchain-agent-provider-map}.
This means any supported provider can be swapped out by changing a single configuration value, without touching scenario code.
Most providers allow to set the \enquote{temperature} of a model,
where lower values produce more deterministic responses, while higher values increase creativity and diversity~\cite{anthropic_model_temperature}.
For our intents and purposes always set \mintinline{python}{temperature=0}, as we want to make agent behavior as deterministic as possible.


\subsection{LangChain Concepts}\label{subsec:ai-scenarios-langchain-concepts}

LangChain provides a framework for developing applications powered by large language models (\gls{LLM}s) and agent-based systems.
It enables developers to combine modular components and external integrations, simplifying \gls{AI} application design while maintaining flexibility as underlying technologies evolve~\cite{langchain_repo}.

The primary LangChain concepts used in the \gls{NSAK} framework are:

\begin{itemize}
    \item \mintinline{python}{BaseChatModel} - provider-agnostic interface for the underlying \gls{LLM}.
    \item \mintinline{python}{BaseTool} - interface for callable tools that the agent can invoke.
    \item \mintinline{python}{create_agent()} - builds a LangGraph-based ReAct agent graph that wires the model and tools together.
    \item \mintinline{python}{messages} - a list of conversation messages (user, \gls{AI}, tool) maintained across the agent's reasoning loop.
\end{itemize}

The listings in the appendix section~\ref{subsec:appendix-ai-agent-core} are showing the agents implementation in detail.
The \mintinline{python}{AiAgent.__init__()} method calls \mintinline{python}{create_model()} to instantiate the provider-specific chat model
and then passes it to \mintinline{python}{create_agent()} together with the tool list and a fixed system prompt that establishes the cybersecurity simulation context.
The \mintinline{python}{run()} method invokes the agent once and streams all resulting messages (user, \gls{AI}, tool calls, tool results) as formatted strings.
The \mintinline{python}{run_interactive()} method extends this into an interactive loop,
where after each agent response the operator is prompted for the next instruction,
and the full conversation history is retained in the \mintinline{python}{messages} list until the operator types an empty line or \mintinline{bash}{exit}.

\subsubsection{Tool Calling Concepts}\label{subsubsec:ai-agent-tool-calling-concepts}

Tool calling is the mechanism by which the \gls{LLM} declares that it wants to invoke an external function.
The framework intercepts the model's output, parses the tool call, executes the corresponding Python function, \gls{MCP}, or Skill,
and appends the result to the message history before asking the model to continue.
This loop repeats until the model produces a final text response with no tool calls.

In \gls{NSAK}, tools can be provided through several complementary mechanisms:

\begin{itemize}
    \item \textbf{LangChain Tools} - native Python functions decorated with \mintinline{python}{@tool},
    which LangChain automatically wraps with type-safe \gls{JSON} schemas for the model.
    This is the primary mechanism used for \gls{NSAK}-specific tools (host configuration, \gls{CLI} access, e-mail, human interaction hook).
    Further, all \gls{NSAK} drills are wrapped as LangChain tools via \mintinline{python}{generate_drill_tools()},
    giving the agent type-safe access to all drill capabilities.
    \item \textbf{\gls{MCP}} - the Model Context Protocol allows external tool servers to expose additional capabilities;
    used here for the draw.io integration (see~\ref{subsubsec:ai-agent-mcp-integration}).
    \item \textbf{\gls{CLI} Access} - the \mintinline{python}{cli_tool} gives the agent direct shell access,
    allowing it to run any installed binary (nmap, tshark, etc.).
\end{itemize}

\subsubsection{Tool Calling Models}\label{subsubsec:ai-agent-tool-calling-models}

Considering its limited size of 7 billion parameters, the results were considered satisfactory in the first test model \enquote{qwen2.5:7b-coder}.
But as it turns out, not all models are capable of calling tools.
Often, multiple variants of the same model are available, and they don't only differ in size,
but also for different strengths or capabilities such as tool calling.
The tool calling variants are often have the suffix \enquote{instruct}.
Luckily, \enquote{qwen2.5:7b-coder} has such variant called \enquote{qwen2.5:7b-instruct}.

The \mintinline{python}{create_ai_agent()} factory function shown in listing~\ref{lst:langchain-agent-create-ai-agent} is the central assembly point used by all three \gls{AI} scenarios.
It reads the \mintinline{python}{ai} configuration block, assembles the tool list (always including \mintinline{python}{cli_tool},
\mintinline{python}{host_configuration}, and \mintinline{python}{send_email}), optionally adds the human interaction hook or drill tools,
loads \gls{MCP} tools with graceful fallback, and returns a configured \mintinline{python}{AiAgent} instance.

The \mintinline{python}{enable_drill_tools} flag, when set to \mintinline{python}{True}, calls \mintinline{python}{generate_drill_tools()}, which dynamically wraps every \gls{NSAK} drill as a type-safe LangChain tool.
This gives the agent access to structured capabilities such as \mintinline{bash}{discover_hosts} and \mintinline{bash}{port_scan} without requiring \gls{CLI} invocation.

\subsubsection{MCP Integration}\label{subsubsec:ai-agent-mcp-integration}

The \gls{MCP}~\cite{anthropic-mcp} is an open protocol that standardises how \gls{AI} models connect to external tool servers.
Rather than implementing tool calling ad-hoc, \gls{MCP} servers expose a well-defined interface that any compatible \gls{LLM} framework can consume~\cite{mcp-landscape}.
LangChain Agents must be invoked in an event loop to properly support \gls{MCP}, this forced us to refactor the implementation \enquote{ai\_agent.py} to be async.
Furthermore, support for asynchronous drills and scenarios needs to be added, as otherwise the \gls{AI} agent cannot operate in these contexts.
\gls{NSAK} integrates an external draw.io \gls{MCP} server to allow the \gls{AI} agent to create and manipulate diagrams during a scenario run.

\gls{MCP} tools are loaded asynchronously inside \mintinline{python}{create_ai_agent()} and appended to the tool list.
If the server is unavailable, the exception is caught and logged as a warning so the scenarios can still run without diagram support.

\subsubsection{LangChain Tool: Host Configuration}\label{subsubsec:langchain-tool-host-configuration}

The \mintinline{python}{host_configuration} tool shown in listing~\ref{lst:langchain-tool-host-configuraiton} gives the agent a structured view of the host's current configuration.
It returns a dictionary containing the loaded device configuration with interface names, \gls{IP} addresses,
and the \mintinline{python}{is_target} / \mintinline{python}{is_management} flags loaded from the device \gls{YAML}.
This bootstraps the agent's situational awareness without requiring it to run \mintinline{bash}{ip addr}
or parse raw network output - the agent knows from the start which interfaces are part of the attack surface and which are for management traffic.


\subsubsection{LangChain Tool: CLI Tool}\label{subsubsec:langchain-tool-cli-tool}

The \mintinline{python}{cli_tool} shown in listing~\ref{lst:langchain-tool-cli-tool} allows the \gls{AI} agent to execute arbitrary shell commands with a configurable timeout (default 120 s).
It returns a tuple of \mintinline{python}{(exit_code, stdout, stderr)}, giving the agent full feedback to diagnose failures and adapt its next action.
The scope is intentionally broad: the agent can invoke nmap, tshark, apt, or any other binary available in the execution environment.
Besides the execution of drills, this flexibility is what makes the \gls{AI} scenarios powerful,
but it is also why the kill switch described in~\ref{subsec:ai-scenarios-implementation-cli-kill-switch} is a necessary safety measure.


\subsection{Human Interaction Hook}\label{subsec:ai-scenarios-implementation-human-interaction-hook-via-cli}

\subsubsection{LangChain Tool: Human Interaction Hook}\label{subsubsec:langchain-tool-human-interaction-hook}

We implemented a simple LangChain python tool which allows a human operator to interact with the agent~\ref{lst:langchain-tool-human-interaction-hook}.
If enabled via the \mintinline{python}{interactive} flag when calling the \mintinline{python}{create_ai_agent()} function,
the agent can pause its execution and ask the operator a question, then incorporate the answer into its next reasoning step.


\subsubsection{LangChain Middleware: Human in the Loop (HITL)}\label{subsubsec:langchain-midleware-human-in-the-loop}

After the implementation we read in the LangChain documentation,
that it has its own middleware for allowing human interactions,
called \href{https://docs.langchain.com/oss/python/langchain/human-in-the-loop}{Human-in-the-loop}.
We speculated that this solution is more sophisticated than the few lines of python we wrote and tried to refactor our implementation accordingly.
It turned out, that it required a lot more changes than we first thought and the proof-of-concept did not work as stable as the current tool based implementation.
As we focus on the agents non-interactive mode for the evaluation,
we don't want to spend more time on this potential improvement.
For these reasons we decided not to merge the code and let the implementation as is.
The branch containing the proof-of-concept is still available under~\href{https://gitlab.ti.bfh.ch/gausf1-vonal3/swiss-army-knife-network-sniffer/-/tree/310-human-in-the-loop?ref_type=heads}{310-human-in-the-loop}.

\subsubsection{LangChain Agent Chat UI}\label{subsubsec:langchain-agent-chat-ui}

We did not add the~\href{https://docs.langchain.com/oss/python/langchain/ui}{LangChain Agent Chat UI} because we made some implicit architecture decisions which prevent easy integration.

If we decide to implement it regardless, we would need to redesign and refactor the \gls{AI} Agent implementation, for example by switching to a callback-based output model.

\subsection{Logging}\label{subsec:ai-scenarios-implementation-logging}

\gls{NSAK} uses the standard Python \mintinline{python}{logging} module,
configured with a handler that writes to both stdout and a file in the run directory.
Log levels follow the conventional hierarchy, and each logger is namespaced by module to allow fine-grained filtering.
The logging setup is initialised once at framework startup and is available to all scenarios, drills, and agent components without additional configuration.

\subsubsection{LangChain Agent Logs}\label{subsubsec:ai-scenarios-implementation-langchain-agent-logs}

LangChain provides built-in verbose logging that emits detailed traces of agent reasoning steps, tool invocations, and model responses.
These traces are useful for debugging but are emitted at inconsistent log levels~\textthreequartersemdash~notably,
\gls{AI} responses and tool call results are logged at \mintinline{python}{WARNING} rather than \mintinline{python}{DEBUG},
which pollutes the log output under default configurations.
This behaviour is a known quirk of the LangChain logging integration.

\subsubsection{Remote Logging System: Grafana / Loki}\label{subsubsec:ai-scenarios-implementation-remote-logging-system}

To support the collection from multiple devices and
structured analysis of agent runs across multiple executions,
a self-hosted logging backend was configured using Grafana Loki and the \mintinline{python}{python-logging-loki} package~\ref{subsec:grafana-loki-logging-system}.
On the client side the \href{https://pypi.org/project/python-logging-loki/}{python-logging-loki} package was installed
and provided log handler was added to existing setup.
We went for this method over system logging agents such as promtail,
because this way we can provide more metadata in form of \enquote{tags} on the application level,
instead of relying on of the parsing of text based logs.

\subsection{E-Mail Alerting}\label{subsec:ai-scenarios-implementation-e-mail-alerting}

The python standard library already includes packages for creating and sending E-Mails via \gls{SMTP}.
The \enquote{EmailBackend} implemented to the \gls{NSAK} framework is an opinionated wrapper around those packages
and leverages the previously introduced~\ref{sec:configuration-management-implementation} to set up necessary configuration.
If no \gls{SMTP} configuration is provided as specified in~\ref{lst:email-altering-configuration},
the system will write the E-Mails as logs instead.
The working tool can be seen in actions in the test run of the \gls{AI} Reconnaissance scenario~\ref{subsec:scenario-ai-reconnaissance},
where the operator instructs the agent to send the results via E-Mail.


\subsubsection{LangChain Tool: E-Mail Alerting}\label{subsubsec:langchain-tool-e-mail-alerting}

The \mintinline{python}{send_email} tool shown in listing~\ref{lst:langchain-tool-email-alerting} exposes the \mintinline{python}{EmailBackend} to the \gls{AI} agent.
During a scenario run the agent can autonomously send e-mails to operators - for example,
when the \gls{AI} intrusion detection scenario identifies a suspicious host or the operator instructed the \gls{AI} reconnaissance scenario to send a report.
The recipient of the mail is defined via the configuration management and cannot be changed by the agent, so that the operator always knows which mails where sent and who received them.
Optional \mintinline{python}{cc_recipients} and \mintinline{python}{attachments} parameters allow the agent to inform additional stakeholders or attach diagrams and reports.
For better \gls{traceability} a template is defined, which is filled with meta information including the current scenario and a unique ID,
which can be used to associate the mail in grafana.
Further, the subject line is always prefixed with \mintinline{text}{[NSAK]}, so that operators can filter them in their inbox.


\subsection{CLI Kill Switch}\label{subsec:ai-scenarios-implementation-cli-kill-switch}
It's possible that an \gls{AI}-Agent starts doing unexpected, unwanted or even destructive actions.
This was also identified as a possible risk in the risk assessment~\ref{subsec:risk_assessment}.
This kind of misbehavior, combined with elevated permissions and tool calling capabilities via direct \gls{CLI} access,
could lead to a wide range of issues:

\begin{itemize}
    \item The \gls{AI}-Agent is stuck in a loop while using most system resources.
    \item The \gls{AI}-Agent misconfigures the system, rendering it inaccessible or even unusable.
    \item The \gls{AI}-Agent burns too many \gls{API} credits because of a bug, an inefficient request, or a huge task.
    \item The \gls{AI}-Agent starts an attack against a production network.
\end{itemize}

For these reasons we want to be able to kill a specific or all scenarios as fast as possible.
As a first measure, the project team decided to add this functionality as simple \gls{CLI} commands:

\begin{itemize}
    \item \mintinline{bash}{nsak scenario kill <scenario-id>}: Kill a specific scenario (sends \mintinline{bash}{SIGTERM} to the container)
    \item \mintinline{bash}{nsak scenario killswitch}: Kill all running scenarios
    \item \mintinline{bash}{nsak killswitch}: Alias for \mintinline{bash}{nsak scenario killswitch}
\end{itemize}

\subsection{Scenario: AI Agent}\label{subsec:scenario-ai-agent}

The \gls{AI} Agent scenario is the most generic of the three: it accepts a free-form \mintinline{python}{prompt} argument
and runs the \gls{AI} agent in an interactive loop, maintaining the full conversation history across turns.
This makes it the primary entry point for ad-hoc \gls{AI}-assisted tasks where no dedicated scenario exists yet.
The operator can guide the agent step by step, observe its reasoning, and issue follow-up instructions until they type an empty line or \mintinline{bash}{exit}.

\subsection{Scenario: AI Reconnaissance}\label{subsec:scenario-ai-reconnaissance}

The \gls{AI} Reconnaissance scenario automates host and service discovery on a specified network interface.
It encodes a structured five-step plan directly into the initial prompt: the agent is instructed to call \mintinline{python}{host_configuration} to determine the \gls{IP} addresses and subnets on the interface,
then use the \mintinline{python}{cli} tool to invoke nmap for host scanning, then again for service enumeration, and finally to report all findings including vulnerability indicators.
If the \mintinline{python}{interactive} flag is set, the last step invites the operator to issue follow-up instructions via the \mintinline{python}{human_interaction_hook}.

This prompt-driven approach means the scenario does not contain any network scanning logic itself
~\textthreequartersemdash~the agent decides which nmap flags to use, how to interpret results, and what to scan next.
Listing~\ref{lst:scenario-ai-recon-py} shows the scenario entrypoint and listing~\ref{lst:scenario-ai-recon-yaml} shows its \gls{YAML} interface declaration.

\subsection{Scenario: AI Intrusion Detection}\label{subsec:scenario-ai-intrusion-detection}

The \gls{AI} Intrusion Detection scenario is a proof of concept, as it was specified as \enquote{Should} goal.
It demonstrates a two-phase approach: first it performs host discovery using \mintinline{python}{DrillManager.execute("discover_hosts")},
then it captures live network traffic using \mintinline{bash}{tshark} (a system dependency declared in the scenario \gls{YAML}).
Up to 200 packets are captured over a 60-second window and extracted as \gls{CSV} fields (frame number, source and destination \gls{MAC},
source and destination \gls{IP}, \gls{TCP}/\gls{UDP} destination port, protocol stack, and frame length).

Both the host discovery table and the packet \gls{CSV} are injected into a structured \mintinline{python}{PROMPT_TEMPLATE} that instructs the \gls{AI} to identify at most five suspicious events,
each with source/destination \gls{IP} and \gls{MAC}, protocol, and the reason for suspicion, and to identify any malicious hosts.
By constraining the number of events the prompt keeps the agent's output concise and actionable.
Listing~\ref{lst:scenario-ai-ids-py} shows the full scenario entrypoint and listing~\ref{lst:scenario-ai-ids-yaml} shows its \gls{YAML} interface declaration.
