\section{AI \textendash Scenarios}\label{sec:ai-scenarios-implementation}

This section describes the design and implementation of the milestone \gls{AI} Scenarios~\ref{subsubsec:milestone-ai-scenarios},
which is based on the user story map workshop \gls{AI} Purple Team~\ref{subsec:nsak-scenario-ai-purple-team}.
In the workshop we defined the features which such a scenario may provide and categorized them in \enquote{Must}, \enquote{Could} and \enquote{Should}.
Because of time constraints, we set the focused only on the user stories categorized as \enquote{Must}.
The main goal is to implement an \gls{AI} reconnaissance scenario, which is described in the~\ref{subsec:scenario-ai-reconnaissance}.
But on the way it made sense to also create an intermediary scenario which can run custom prompts~\ref{subsec:scenario-ai-agent}.
Further, we already explored the \gls{AI} based intrusion detection scenario~\ref{subsec:scenario-ai-intrusion-detection} which should be seen as proof of concept, because the corresponding milestone and goals are categorized as \enquote{Should}.

\subsubsection{Tool Calling Models}\label{subsubsec:ai-agent-tool-calling-models}
Considering it's limited size of 7 billion parameters, we were quite happy with our first test model \enquote{qwen2.5:7b-coder}.
But as it turns out, not all models are capable of calling tools.
Often, multiple variants of the same model are available, and they don't only for differ in size,
but also for different strengths or capabilities such as tool calling.
The tool calling variants are often have the suffix \enquote{instruct}.
Luckily, \enquote{qwen2.5:7b-coder} has such variant called \enquote{qwen2.5:7b-instruct}.

\subsection{CLI Kill Switch}\label{subsec:ai-scenarios-implementation-cli-kill-switch}
It's possible that an \gls{AI}-Agent starts doing unexpected, unwanted or even destructive actions.
This was also identified as a possible risk in our~\ref{subsec:risk_assessment} and we
This kind of misbehavior, combined with elevated permissions and tool calling capabilities via direct \gls{CLI} access,
could lead to wide range of issues:

\begin{itemize}
    \item The \gls{AI}-Agent is stuck in a loop while using most system resources.
    \item The \gls{AI}-Agent misconfigures the system, rendering it inaccessible or even unusable.
    \item The \gls{AI}-Agent burns to many credits because of a bug, inefficient request or huge task.
    \item The \gls{AI}-Agent starts an attack against a production network.
\end{itemize}

For these reasons we want to be able to kill a specific or all scenarios as fast as possible.
As a first measure, the project team decided to add this functionality as simple \gls{CLI} commands:

\begin{itemize}
    \item \mintinline{bash}{nsak scenario kill <scenario-id>}: Kill specific scenario
    \item \mintinline{bash}{nsak scenario killswitch}: Kill all scenarios
    \item \mintinline{bash}{nsak killswitch}: Alias for \mintinline{bash}{nsak scenario killswitch}
\end{itemize}
