\chapter{Concepts}\label{ch:concepts}

Before the implementation is presented, this chapter establishes the conceptual designs of the \gls{NSAK} framework.
It wraps up the predecessor project this thesis builds on and defines the resource types —
\textit{Device}, \textit{Environment}, \textit{Drill}, and \textit{Scenario} — that reoccur throughout this work.

\section{Predecessor Project: Project 2}\label{sec:predecessor-project-project-2}

This section summarizes the predecessor project that led to the bachelor's thesis.
The \gls{NSAK} is a cybersecurity framework that operates with the following resources and concepts:
\textit{Devices}, which are physical or virtual machines capable of running the \gls{NSAK}.
The security operation is executed in a network environment and can involve one or more attacks or defense scenarios.
The smallest unit in the framework is a drill, which can be orchestrated in a scenario and chained with other drills.

While the modularity and proof of concept were confirmed, several aspects like enhanced configuration management, \gls{GUI}
or a \gls{REST API} are mentioned for future work.

Some of the goals of this thesis directly address these open points and are defined in the section~\ref{ch:project-goals}.

The \glsxtrshort{NSAK} framework is built around four resource types that were originally defined in \enquote{Project 2}\cite{nsakRepository2026}.
Each resource type has a distinct role in the framework and is stored as a \glsxtrshort{YAML} file in the resource library.

\subsection{Device}\label{subsec:device-concept}

A \textbf{Device} resource describes a physical or virtual machine that is capable of running the \glsxtrshort{NSAK} framework.
It serves as the execution host for scenarios and drills and is typically deployed at a strategic network position to give it the access required for the operations it performs.

A device exposes its network configuration to the framework by declaring its interfaces and their \gls{IP} addresses in its resource \glsxtrshort{YAML}.
As an alternative, a special device with the id \enquote{Unknown} was added, which auto discovers the hosts network configuration.
This allows scenarios and drills to resolve interface names and target addresses without hardcoding network details, making the same scenario portable across different devices and network environments.

\subsection{Environment}\label{subsec:environment-concept}

An \textbf{Environment} represents a specific network topology, including its infrastructure components, hosts, and services~\cite{nsakRepository2026}.
It describes the target network context in which a scenario is intended to operate.
For example, a simple client--server setup over a switch, a \gls{WLAN} access point with connected clients, or a segmented business network.

Environments are referenced by scenarios to make explicit which network context they are designed for, helping operators select and validate the right configuration before executing an operation.

\subsection{Drill}\label{subsec:drill-concept}

A \textbf{Drill} is a self-contained, reusable unit of execution with a specific, well-defined goal~\cite{nsakRepository2026}.
Its goal can be an active or passive attack step, network discovery, traffic capture, a configuration change, or any other discrete action relevant to a red or blue team activity.

Examples of drills include \gls{ARP} spoofing, host discovery via \gls{ARP} scan, transparent \gls{TCP} proxying, traffic capture with T-Shark, and network configuration tasks such as enabling IP forwarding or \gls{NAT}.

Each drill declares the system and Python packages it requires as well as a typed \mintinline{bash}{interface} that lists its input arguments and return type.
The return value of one drill can be consumed as the input of a subsequent drill within a scenario, enabling data to flow through a chain of execution steps.

\subsection{Scenario}\label{subsec:scenario-concept}

A \textbf{Scenario} describes a concrete red or blue team use case and orchestrates a sequence of drills targeted at one or more environments~\cite{nsakRepository2026}.
Where a drill is a single technical reusable and modular building block, a scenario is an implementation of a specific attack or defense operation.

Like drills, scenarios declare a typed \mintinline{bash}{interface} with input arguments, allowing operators to parameterise a scenario at execution time via the \glsxtrshort{CLI} without modifying the scenario definition itself.
This separation keeps scenarios reusable across different network configurations while still allowing runtime flexibility.


\section{Configuration Management}\label{sec:configuration-management-concepts}

The \glsxtrshort{NSAK} framework distinguishes three configuration layers, each with a different scope and lifetime.
Keeping them separate avoids coupling concerns that change at different rates and makes it easier to reason about where a given piece of configuration comes from.

\subsection{Static Configuration}\label{subsec:static-configuration-concept}

The static configuration layer involves values which are specific for a deployment and are very unlikely to change after the initial provision of the \gls{NSAK} device.
It mainly establishes the filesystem layout that all other parts of the framework depend on.
For example, where the resource library is located, where runtime data is written, and what the base directory of the installation is.

\subsection{Runtime Configuration}\label{subsec:runtime-configuration-concept}

The runtime configuration layer holds mutable state, which might be changed by an operator via the \gls{CLI}.
It is stored as a \glsxtrshort{YAML} file, which is currently loaded at the start of every invocation.
If no configuration file exists yet, a default is created automatically on first access, so no explicit initialization step is required from the user.

\subsection{Resource Configuration}\label{subsec:resource-configuration-concept}
The resource configuration layer is provided by the resource library rather than the framework core.
Each resource declares its own configuration inside a \glsxtrshort{YAML} file stored alongside its implementation.
The framework reads these files to discover and load resources at runtime.

\subsubsection{Typed Interface Arguments}\label{subsubsec:typed-interface-arguments}
Drills and scenarios declare a typed \mintinline{bash}{interface} in their resource configuration \glsxtrshort{YAML} file, that lists the arguments with an explicit type annotation and an optional default value.
The framework reads these annotations at runtime and automatically generates the correct \glsxtrshort{CLI} options for each resource.
This means that adding a new argument to a drill or scenario immediately exposes it as a typed \glsxtrshort{CLI} option without requiring any changes to the framework or the \glsxtrshort{CLI} code.

\subsubsection{Mergeable YAML Structure}\label{subsubsec:mergeable-yaml-structure}
All resource \glsxtrshort{YAML} files follow a common structure in which resources are nested under a resource-type key (e.g.\ \mintinline{bash}{drills:}, \mintinline{bash}{scenarios:}).
This structure ensures that \glsxtrshort{YAML} files from different parts of the library could be merged into a single in-memory data structure without key conflicts, which is a prerequisite for supporting multiple library paths and composite library configurations in the future.

Together, the resource model and the layered configuration system define how the \gls{NSAK} framework is structured and operated.
Whether the design and especially, \gls{AI}-driven scenarios, can compare tho a manual implemented needs to be accessed.
Therefore, the methodology to address this questions are introduced in the next chapter.
